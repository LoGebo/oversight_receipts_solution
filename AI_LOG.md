# AI collaboration log

## How I worked with the assistant
I used AI coding assistants as a tool, in the way the brief expects: they wrote code, ran experiments, drafted text and ran audits; I set the direction, chose what to build, read the data and the results, and decided what to keep or throw away. The decisions behind the system are mine, and so are the points where I stopped the assistant or sent it back.

## What I contributed: design and judgment about the data
1. **Fraud that the deterministic engine lets through.** I asked for many synthetic histories that the engine, with all its rules, classifies as `pass` but that are real fraud, so a fine-tuned model has a task the rules cannot already do. This is the core idea of the extension, and it came from how I understand what language models add on top of rules.
2. **A second-line, cross-receipt reviewer.** I saw that the engine judges one receipt at a time and misses patterns across a month (split spend, a repeated merchant, duplicates). I specified the design: the engine keeps the verdict and the reviewer can only escalate `pass → review`.
3. **Red-team agents to remove my own bias.** I asked agents to invent evasion schemes I had not thought of, so the catalogue does not only reflect my imagination.
4. **An exam independent of the training data.** I insisted the exam cannot come from the generator that produced the training data, otherwise the score is inflated, and proposed using the 32 official receipts as the reference set.
5. **Same-family blind spots.** I pointed out that models of one family share blind spots, and that data generated by one provider's models biases a comparison against that provider's frontier models. I asked for data and checks from other model families.
6. **A blind audit of the synthetic labels** with a different model, before trusting them.
7. **Questions about the split and the numbers.** I asked whether the split made sense for evaluating the model and whether a number was a real evaluation or just the labels we built.
8. **Challenging the assistant's claims.** When it said the cases were rule-detectable, I asked it to argue it, which led to the framing "the model discovers, the rules enforce".
9. **Asking to be challenged.** I asked it to remove my biases and not to agree with me. It admitted it had been agreeing too much and gave me data (the classifier was already near-perfect on the lines, so there was little room to win there).
10. **Seeing the official answers first.** I asked to look at the answer key before the architecture, to understand the data.
11. **Pressure-testing stated limits.** I questioned the out-of-scope receipts and why TIME-04 cannot be measured; both were checked against the code and the data.

## What the assistant got wrong, and how it was caught
| # | What the AI got wrong | How it was caught | Outcome |
|---|---|---|---|
| A-001 | A research agent reported an industry case-study result as "94% vs 98%". | A separate fact-checking agent tried to refute it and could not confirm the 98%. | Dropped; only sourced numbers are quoted. |
| A-002 | The multi-agent plan said "~20 h" in several places while its own day-by-day table summed to ~22 h. | The completeness-critic agent recomputed the totals. | The plan uses the table. |
| A-003 | The plan treated rule details (supersession, the EXC-02 reading) as settled although the agents had only seen summaries. | The critic flagged them as "digests not verified". | Rules are re-read from the policy files; each ambiguity becomes a logged decision. |
| A-004 | The synthetic training data had a weekend shortcut: every clean month had weekend receipts and the fraud months did not, so the model learned the generator's style. | It lost on the independent exam; a counterfactual experiment then confirmed it (adding one harmless Saturday receipt to clean months dropped escalation from 100% to 6%). | The earlier results are marked inflated; the data generator was rebuilt with the same sampler for both classes and an anti-shortcut gate. |
| A-005 | Opus 4.5 results through the API did not represent the model: a request parameter the model rejects had been sent. | The numbers were not comparable with the other runs, so the request code was checked. | Fixed; the earlier numbers are marked invalid. |
| A-006 | The README draft said "temperature 0", but the Anthropic path sends no temperature (the model rejects it). | The final audit I ordered, with defined checks, compared the README with the code. | README states the real mechanism: the committed cache keyed by a hash of model, prompt and content. |
| A-007 | The AWS cost used the token counts of an older prompt version, not the final one. | The same audit recomputed the cost from the run records. | Figures recomputed: $579-788 model, about $630-930 per month in total. |
| A-008 | The first redesign of the viewer rendered `$` amounts as maths, showed high confidence in red and a critical exception in grey. | Looking at screenshots of the pages, not the code. | Fixed and checked again in the browser. |

## How I verified
- The answer key is physically separated from the pipeline, with a test that fails if it leaks (`tests/test_no_leak.py`).
- The keyword baseline was frozen by hash before scoring.
- For the extension, the success criteria were written down before any result (`finetune/FINETUNE_LOG.md`).
- Label quality of the synthetic set was audited blind with a second model.
- Five independent read-only reviewers audited the finished work (brief compliance, engine against policy text, evaluation, viewer, architecture and AWS); one recomputed every headline metric from the raw files and matched them.
- I questioned stated limits instead of accepting them (out-of-scope receipts, TIME-04) and had them checked.

## Assistants used
Claude Code was the main assistant (planning, code, experiments, audits). Other model families were used as second opinions and as data generators for the fine-tuning extension.
